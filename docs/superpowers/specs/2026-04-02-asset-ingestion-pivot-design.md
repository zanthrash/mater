# Asset Ingestion Pivot — Design Spec

**Date:** 2026-04-02
**Status:** Draft
**Approach:** Surgical Pivot (reuse existing infrastructure, reshape data layer and screens)

## Context

Mater is pivoting from a heavy equipment inspection app to a **heavy equipment asset ingestion** application for auction companies. When a piece of equipment arrives at the yard, a worker uses the app to quickly capture photos, VIN/serial data, and let AI extract a rich asset record — classified by taxonomy, populated with type-specific specs, and immediately available via API for downstream systems (auction platforms, inspection tools, etc.).

The inspection workflow (condition assessment, PDF reports) is removed. The core AI analysis, VIN lookup, and camera infrastructure are retained and enhanced.

**Target audience:** Heavy equipment auction yard workers performing intake.
**Demo target:** VP of Engineering — the demo flow is: ingest an asset on the phone, then hit the API to show the data is immediately available downstream.

---

## 1. Wizard Flow

The current 8-step inspection wizard becomes a 6-step intake flow:

| Step | Screen | Description |
|------|--------|-------------|
| 1 | **Home / Asset List** | Browse ingested assets. Tap "+" to start new intake. |
| 2 | **Overview Photo** | Capture the hero shot of the equipment. |
| 3 | **VIN / Serial Entry** | Manual entry or camera scan. VIN lookup fires on submit. After VIN step completes, the **early classification AI call** fires using overview photo + VIN data to determine taxonomy and generate the photo checklist. |
| 4 | **Guided Photos** | Photo checklist dynamically generated by AI based on equipment type. Worker captures each suggested shot. Can retake, delete, or add extra photos. Minimum 3 photos required. |
| 5 | **Review & Edit** | Single editable screen showing all extracted data: taxonomy, core specs, type-specific specs, yard metadata. AI + VIN conflicts highlighted inline (VIN pre-selected, worker can override). |
| 6 | **Success** | Asset saved. Shows asset ID, thumbnail, key details. "View in List" or "Ingest Another." |

### Removed from current app
- Condition Assessment screen (5-section rating)
- Dedicated Conflict Resolution screen (merged into Review)
- PDF generation
- Inspector Name field

### Added
- Home / Asset List screen
- Guided Photo Checklist screen
- Taxonomy classification display
- Type-specific specs
- Yard metadata fields (lot number, consignor, yard location)
- Asset Detail view (read-only)

## 2. Data Model

Two core tables replace the single `inspections` table.

### `assets` table
The canonical record of what this piece of equipment is.

| Column | Type | Purpose |
|--------|------|---------|
| id | uuid PK | Auto-generated |
| created_at | timestamptz | When first ingested |
| updated_at | timestamptz | Last modified |
| vin_serial | text | VIN or serial number |
| category | text | Top-level taxonomy (e.g., "Earthmoving") |
| type | text | Equipment type (e.g., "Excavator") |
| subtype | text nullable | Equipment subtype (e.g., "Mini Excavator") |
| make | text | Manufacturer |
| model | text | Model name/number |
| year | integer | Model year |
| engine_type | text nullable | Fuel/engine type |
| transmission | text nullable | Transmission type |
| gvw_lbs | integer nullable | Gross vehicle weight |
| hours_on_meter | integer nullable | Hour meter reading |
| type_specific_specs | jsonb | Dynamic specs varying by equipment type |
| lot_number | text nullable | Yard lot assignment |
| yard_location | text nullable | Physical location on the yard |
| consignor | text nullable | Seller/consignor name |
| photos | jsonb | Array of `{ url, label, type }` |
| status | text | Default "ingested". Future values ("listed", "sold") are out of scope for this POC. |

### `intake_events` table
Audit trail of what happened during ingestion.

| Column | Type | Purpose |
|--------|------|---------|
| id | uuid PK | Auto-generated |
| asset_id | uuid FK | References assets.id |
| created_at | timestamptz | When intake occurred |
| operator_name | text nullable | Who performed the intake |
| gps_lat | numeric nullable | GPS latitude |
| gps_lon | numeric nullable | GPS longitude |
| ai_analysis_result | jsonb | Raw Claude spec extraction response |
| vin_lookup_result | jsonb | Raw NHTSA/Claude VIN response |
| ai_taxonomy_result | jsonb | Raw taxonomy classification from AI |
| source_photos | jsonb | Photo references sent to AI |

### `taxonomy` table
Seeded reference data for equipment classification.

| Column | Type | Purpose |
|--------|------|---------|
| id | uuid PK | Auto-generated |
| category | text | Top-level category |
| type | text | Equipment type |
| subtype | text nullable | Equipment subtype |

## 4. AI Analysis

### Two-call architecture

**Call 1: Early Classification** (fires after overview photo + VIN data)
- **Input:** Overview photo + VIN/serial (if available)
- **Output:**
  - `taxonomy`: `{ category, type, subtype, confidence }`
  - `photoChecklist`: `string[]` — suggested photos for this equipment type
- **Purpose:** Drive the guided photo checklist screen
- **Endpoint:** `POST /api/analyze/classify`

**Call 2: Full Spec Extraction** (fires after all photos captured)
- **Input:** All photos (overview + guided + extras) + VIN data + classified taxonomy
- **Output:**
  - `coreSpecs`: `{ make, model, year, engineType, transmission, gvwLbs, hoursOnMeter }`
  - `typeSpecificSpecs`: dynamic key-value pairs relevant to the equipment type (e.g., `{ bucketCapacity: "1.2 cu yd", boomReach: "24 ft", maxDigDepth: "18 ft" }`)
  - `confidenceScore`: overall confidence
- **Purpose:** Populate the review screen
- **Endpoint:** `POST /api/analyze/images` (updated prompt)

### Conflict handling on Review screen
- Where AI and VIN disagree on a field, the field is highlighted
- VIN value is pre-selected for identity fields (make, model, year) — higher trust source
- Worker can tap to switch to AI value or type their own
- Non-conflicting fields show the available value directly

### Taxonomy fallback
- If AI classification confidence is low, or the AI call fails, the review screen shows taxonomy picker dropdowns populated from the `taxonomy` table
- Worker can always override AI taxonomy on the review screen

### Photo checklist fallback
- If classification call fails, use a generic checklist: `["Front", "Rear", "Left Side", "Right Side", "Interior", "Engine", "Serial Plate"]`

## 5. Guided Photo Checklist

### Screen behavior
- Displays a list of photo items from the AI classification response
- Each item shows: label, camera icon (uncaptured) or thumbnail with green checkmark (captured)
- Tapping an uncaptured item opens the camera for that shot
- Captured photos show two actions:
  - **Retake** — reopens camera, replaces the existing photo
  - **Delete** — removes the photo, returns item to uncaptured state
- "Add Extra Photo" button at the bottom for unlisted shots
- Extra photos can also be deleted
- Minimum 3 photos required to proceed
- Continue button enabled once minimum is met

### Photo data structure
```typescript
interface AssetPhoto {
  url: string        // Supabase storage URL (after upload)
  uri: string        // Local URI (before upload)
  label: string      // e.g., "Cab Interior", "Custom"
  type: 'guided' | 'extra'
}
```

## 6. Home Screen / Asset List

### Layout
- **Top bar:** App title ("Mater") + "+" FAB or button to start new intake
- **Search bar:** Filter by make, model, VIN/serial, or lot number
- **Asset cards:** Scrollable list sorted by intake date (newest first), each showing:
  - Overview photo thumbnail
  - Make / Model / Year
  - Category > Type (e.g., "Earthmoving > Excavator")
  - Lot number (if assigned)
  - Intake date
- **Empty state:** Friendly message + prominent "Ingest Your First Asset" button

### Asset Detail View
Tapping a card opens a read-only detail view:
- Full-size photo gallery with labels (swipeable or grid)
- All asset data organized in sections: Taxonomy, Core Specs, Type-Specific Specs, Yard Metadata
- Intake event history at the bottom (operator, date, location)

## 7. Review & Edit Screen

Single screen replacing both the old AI Result screen and Conflict Resolution screen.

### Sections
1. **Taxonomy** — Category / Type / Subtype with editable dropdowns (populated from taxonomy table). AI-proposed values pre-filled. If AI confidence was low, highlighted for attention.
2. **Core Specs** — Make, Model, Year, Engine Type, Transmission, GVW, Hours. Editable text/number fields. Conflicts between AI and VIN highlighted with both values shown; VIN pre-selected for identity fields.
3. **Type-Specific Specs** — Dynamic key-value fields based on what the AI extracted. Worker can edit values or add new key-value pairs.
4. **Yard Metadata** — Lot Number, Yard Location, Consignor. Manual entry fields.
5. **Photos** — Thumbnail grid of all captured photos with labels. Read-only on this screen (editing happens on the photo screen via back navigation).

### Submit behavior
- "Save Asset" button at bottom
- Calls `POST /api/assets` with all data
- On success, navigates to Success screen

## 8. API Endpoints

### New endpoints
| Method | Path | Purpose |
|--------|------|---------|
| GET | `/api/assets` | List assets. Filters: `category`, `type`, `make`, `status`, `search` (free text). Paginated via `limit` + `offset`. |
| GET | `/api/assets/:id` | Full asset detail including photos and type-specific specs. |
| GET | `/api/assets/:id/intake-events` | Intake event history for an asset. |
| POST | `/api/assets` | Create asset + intake event. Uploads photos to storage. |
| PUT | `/api/assets/:id` | Update asset fields. |
| GET | `/api/taxonomy` | Returns full taxonomy tree grouped by category. |
| POST | `/api/analyze/classify` | Early classification: overview photo + VIN → taxonomy + photo checklist. |

### Modified endpoints
| Method | Path | Change |
|--------|------|--------|
| POST | `/api/analyze/images` | Updated AI prompt for taxonomy-aware spec extraction. |

### Removed endpoints
| Method | Path | Reason |
|--------|------|--------|
| POST | `/api/inspections` | Replaced by `POST /api/assets` |
| GET | `/api/inspections/:id` | Replaced by `GET /api/assets/:id` |

### Retained as-is
| Method | Path |
|--------|------|
| POST | `/api/analyze/vin` |
| POST | `/api/analyze/vin-ocr` |
| GET | `/health` |

## 12. Verification Plan

### End-to-end demo flow
1. Open app → see empty asset list with "Ingest Your First Asset"
2. Tap "+" → capture overview photo
3. Enter/scan VIN → see VIN lookup results
4. App shows guided photo checklist based on AI classification
5. Capture photos, retake one, delete one, add an extra
6. Review screen shows all data: taxonomy, specs, yard metadata, conflicts highlighted
7. Edit a field, fill in lot number and consignor
8. Save → success screen
9. "View in List" → see asset in the list
10. Tap asset → see full detail view
11. Hit `GET /api/assets` from terminal → see the asset data
12. Hit `GET /api/assets/:id` → see full rich record

### API verification
- `GET /api/assets` returns paginated list with filters working
- `GET /api/assets/:id` returns complete asset with photos, specs, taxonomy
- `GET /api/assets/:id/intake-events` returns intake audit trail
- `GET /api/taxonomy` returns full taxonomy tree
- `POST /api/analyze/classify` returns taxonomy + photo checklist from a photo

### Unit/integration tests
- Asset creation and retrieval via repository
- Taxonomy seeding and lookup
- AI prompt returns expected shape
- VIN + AI conflict merging logic
